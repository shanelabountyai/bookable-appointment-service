A headline correctness metric that is unfalsifiable teaches the wrong lesson, which is disqualifying in a learning project. Cost: a `docker-compose.yml`. This repo owns **port 3300** (storage has 3000, rental has 3100) — set it as the config default, per the rental footgun writeup. |
| D-2 | What enforces "no double-booking" | **The database. A partial gist exclusion constraint on `(providerId, tstzrange(blockedStart, blockedEnd, '[)')) `, `WHERE status NOT IN (terminal set)`, in a hand-written migration.** Application code writes and maps SQLSTATE `23P01` → `SlotTaken` → 409; it never checks-then-writes as the correctness mechanism. | This is the schema-determining decision the draft left open, and it is item-one work: buffers live **inside** the stored blocked range (`blockedStart = startAt − bufferBefore`, `blockedEnd = endAt + bufferAfter`, stored columns); intervals are half-open everywhere or back-to-back bookings false-conflict; `READ COMMITTED` suffices *because* the constraint exists — no retry loop, no SERIALIZABLE (spec §4.3). Time off and ad-hoc blocks are **separate tables, outside the constraint** — deliberately, because AVAIL-05 requires that blocking over an existing booking *surface* the conflict for a human, not be refused by the database. A test must provoke a real `23P01` (Prisma will not surface it as `P2002`) and a test must insert directly against the database and be refused. |
| D-3 | Time representation | **Two axes, branded, non-interchangeable: `CalendarDay`/`WallTime` (rules) vs `Instant` (occurrences). One conversion module; its `resolve()` returns `unique \| gap \| ambiguous`, never a bare instant. `CalendarDay` is stored `CHAR(10)`, never `@db.Date`.** | Rules (weekly windows, override days) are wall-clock; everything booked is an instant; the engine unions windows *after* resolution, never before (spec DST-7). Banned repo-wide by lint: `new Date(string)`, `Date.parse`, `get/setHours`, `toISOString().slice(0,10)`, `getTimezoneOffset`. Prisma `@db.Date` is banned because Postgres `date` → JS `Date` is the exact path that cost rental R-042 a day-west shift with ten green tests. CI runs the suite under `TZ=Pacific/Kiritimati` and `TZ=UTC` and asserts byte-identical output — a UTC-only CI lets axis-crossings ship. Temporal (via `temporal-polyfill`) at the boundary only; the engine core does integer epoch-millis arithmetic, which is DST-proof by construction and keeps the pure function library-free. |
| D-4 | Slot identity & grid | **A slot's identity is its instant. No URL, token, form, or job payload ever carries `{date, time}` — on fall-back day "01:30" names two instants and such a payload is a coin flip. Grid anchors to window-open, not local midnight.** | The booking POST takes an instant (offset-bearing ISO string). Fall-back's doubled hour is offered as two distinct slots with the offset visible (`labelIsAmbiguous`); spring-forward's missing hour produces no labels and a POST for a nonexistent local time is refused, never coerced. `'local-midnight'` anchoring shifts the whole grid twice a year; window-open is stable. Labels are precomputed server-side in the business zone — the browser's zone renders at most a secondary "your time" line. |
| D-5 | Manage-token lifetime | **Multi-use until `appointment.end + 24h`, scoped to one appointment, revocable by reissue, re-pointed (not reissued) on reschedule.** Rental D-16, same reasoning, same direction: the draft's "used tokens fail safely" is rejected. | Confirm-then-later-cancel and reschedule-twice are the *ordinary* customer workflow; a single-use token fails on step two of every appointment. Single-use remains correct where a token establishes a session (staff password reset). The control set instead: single-appointment scope, expiry, revocation on reissue, rate limiting on the route, and D-10's no-internal-identifiers rule with a test. |
| D-6 | Reschedule mechanics | **Reschedule is an event on a surviving appointment — a single-row `UPDATE` inside one transaction that re-runs the engine, plus an `AppointmentEvent` recording both sides. It is not a status, not a cancel-then-book, and not a new row.** | The PO review proposed old-row-`rescheduled` + new row; the concurrency spec showed why same-row wins and the tiebreak is the token: a new row kills the manage link at exactly the moment the customer is using it, and cancel-then-book across two transactions can leave the customer with *no* appointment (spec §4.6, four failure modes). History survives in the event log, which is append-only — nothing is lost by updating the row. The exclusion constraint checks the updated row against *other* rows only, so a move overlapping its own old time does not false-conflict. Cancellation-rate reporting reads events and excludes reschedules (RPT-03). Customer reschedule obeys the cancellation cutoff (APPT-05) — otherwise the cutoff is decorative. |
| D-7 | Lifecycle shape | **Eight states — `booked, confirmed, checked_in, in_progress, completed, no_show, cancelled, cancelled_late` — with the §7 transition table normative, `confirmed` given a real trigger, actual-vs-scheduled timestamps, and staff-only terminal corrections within 7 days.** | Adopts operator recs 1, 6, 7 wholesale: a book that cannot represent "actually started" or "running late" is a paper-book generator; `cancelled_late` split from `cancelled` because lumping them makes the cancellation report unactionable; `no_show ↔ completed` corrections exist because mis-taps are daily and the alternative is SQL surgery. | D-8 | Staff overrides vs Goal 2 | **"Impossible" means impossible *by accident*. Customer self-serve can never create a conflict. Mechanically the constraint stays absolute and overrides are *modeled*: an override booking writes `blockedStart = blockedEnd` (zero-width range participates in no `&&` overlap) plus `overriddenFromRange` for display, so the constraint never lies and the day view renders the true collision. The alternative (dropping the constraint to app-level checks for staff) re-opens the accidental-double-book hole and is rejected. |

| D-15 | The constraint's partial predicate | **`WHERE status NOT IN ('cancelled','cancelled_late')`** — derived in code from the single status module (D-7), never hand-typed in two places. **Supersedes the literal SQL in `03-slot-engine-spec.md` §4.2**, which predates D-7's split. | Three documents disagreed: the spec says `<> 'cancelled'`, D-2 says "the terminal set", CLAUDE.md says "active statuses". The spec's version blocks every `cancelled_late` slot forever — the salon late-cancels a Saturday colour and can never resell it, which is exactly the perishable-supply loss the waitlist exists to recover. | D-16 | Overrides and the busy set | **The busy-set query returns `COALESCE("overriddenFromRange", tstzrange("blockedStart","blockedEnd",'[)'))`. `overriddenFromRange` is a `tstzrange` column, NOT NULL exactly when the row is an override.** The constraint continues to see only the zero-width range. | Closes a hole that would have failed only at runtime and only after an override. D-8 has an override write `blockedStart = blockedEnd`, an **empty** range that participates in no `&&` — correct for the constraint. But the busy-set predicate (`blockedEnd > windowStart AND blockedStart < windowEnd`) returns that row as a **zero-width `BusyInterval`**, which subtracts nothing from the grid, so the engine offers the overridden time to the public booking flow. Staff knowingly double-book Dana at 2pm → the website offers Dana 2pm → a customer books it → Dana is triple-booked and the third one was *accidental*, violating Goal 2 and D-8's own "customer self-serve can never create a conflict". CLAUDE.md named the day view as the reader of `overriddenFromRange`; the engine is the reader nobody listed. |

| D-22 | Running late is first-class | **A provider's running-late state is a stored per-provider-per-day delta, NOT a rewrite of `startAt`.** The engine consumes it as a `BusyInterval` of kind `running-late`, excluded with reason `provider-running-late`. Storing a delta rather than rewriting `startAt` matters because a rewrite changes the time on the confirmation the client is already holding. | D-23 | Multi-service visits are in v1 (answers the §3/§10 contradiction) | **One visit, one provider, several services IS in v1 as VISIT-01.** Durations compose into a single body; buffers do **not** stack between lines of one visit (the first line's `bufferBefore` and the last line's `bufferAfter` only). One `Appointment`, one `AppointmentServiceLine` per service. Multi-**provider** chains remain Phase 3. | `00-master-prd.md` §3 said single-provider multi-service visits were in scope as VISIT-01 while §10 listed multi-service visits under Phase 3, and VISIT-01 existed nowhere else in the repo — half the sample business's Saturday book (cut + colour) resting on a contradiction. The deciding factor is that the *workaround is refused by the database*: two adjacent appointments have overlapping blocked ranges once cut's `bufferAfter` meets colour's `bufferBefore`, so staff would have to click a knowing override on every combination booking, all day — which trains them to dismiss the override marker that D-8 depends on being meaningful. Costs nothing structurally: `AppointmentServiceLine` is already plural-shaped (D-12) and the engine needs no change, since a composed duration is just a longer service. |
| D-24 | Serializing the booking write path | **The booking transaction takes a transaction-scoped advisory lock on `(providerId, businessDay)` before re-running the engine.** It is NOT the correctness mechanism for overlap — the D-2 exclusion constraint remains that, and is still tested against a writer that bypasses the lock. The lock closes the one gap the constraint deliberately does not cover. | A staff override stores a ZERO-WIDTH blocked range (D-8) so the constraint stays absolute without refusing the override — which means the constraint does **not** defend overridden time, and only the in-transaction engine re-check does (operator review R-9). Two concurrent transactions — a staff override and a self-serve booking of the same range — would both pass their re-checks and both commit, producing exactly the accidental double-book Goal 2 forbids. `pg_advisory_xact_lock` locks a KEY rather than a row, so it works before the row exists (`SELECT ... FOR UPDATE` cannot: the first booker of a slot finds nothing to lock), and the `_xact_` variant is released at COMMIT/ROLLBACK with no cleanup path to forget. Scope is one provider-day, so it costs nothing at salon scale. **Consequence worth knowing:** the spec's scripted "A reads, B reads, B commits, A writes → A gets 23P01" interleaving is no longer reachable through the write path — the loser now re-runs the engine after the winner commits and finds the time occupied. That is a stronger guarantee, and the write path maps an occupied slot to the same `SlotTaken` → 409 the constraint violation maps to, so the caller cannot tell the difference. The constraint's own defence is proven by a separate test that bypasses the lock. Prisma's interactive-transaction timeout is raised to 15s because queue time behind the lock counts against it and would otherwise surface as P2028, which looks nothing like a conflict. |
