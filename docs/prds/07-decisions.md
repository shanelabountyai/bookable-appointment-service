# Decision Log — Bookable

**Status:** D-1 through D-13 recorded 2026-08-14 at project setup, from the three-review pass on draft v1 (`docs/reviews/`). Conventions carried from the storage (`B-`) and rental (`R-`) builds are cited by their decision numbers there.
**Precedence:** This document amends the PRDs. Where a PRD conflicts with a decision below, this document wins. When building from the backlog, treat each decision as settled — do not re-open unless the owner amends this log. Append new decisions with new D-numbers; never edit a settled row's meaning.

| # | Topic | Decision | What it means for the build |
|---|---|---|---|
| D-1 | Tech stack & database | **Same stack as the siblings, and Postgres from commit one — the draft's "start SQLite (non-blocking)" is rejected as wrong in both halves.** | Next.js (App Router) + TypeScript, Postgres + Prisma, Tailwind + shadcn, Vitest + Playwright + axe, monorepo `apps/web` + `packages/core` + `packages/db`, Vercel target. SQLite is not non-blocking: it has no `EXCLUDE` constraint (the D-2 invariant cannot even be declared) and permits one writer per database file, so the P0 race test *cannot fail* — it measures the storage engine, not the code (spec §4.4). A headline correctness metric that is unfalsifiable teaches the wrong lesson, which is disqualifying in a learning project. Cost: a `docker-compose.yml`. This repo owns **port 3300** (storage has 3000, rental has 3100) — set it as the config default, per the rental footgun writeup. |
| D-2 | What enforces "no double-booking" | **The database. A partial gist exclusion constraint on `(providerId, tstzrange(blockedStart, blockedEnd, '[)')) `, `WHERE status NOT IN (terminal set)`, in a hand-written migration.** Application code writes and maps SQLSTATE `23P01` → `SlotTaken` → 409; it never checks-then-writes as the correctness mechanism. | This is the schema-determining decision the draft left open, and it is item-one work: buffers live **inside** the stored blocked range (`blockedStart = startAt − bufferBefore`, `blockedEnd = endAt + bufferAfter`, stored columns); intervals are half-open everywhere or back-to-back bookings false-conflict; `READ COMMITTED` suffices *because* the constraint exists — no retry loop, no SERIALIZABLE (spec §4.3). Time off and ad-hoc blocks are **separate tables, outside the constraint** — deliberately, because AVAIL-05 requires that blocking over an existing booking *surface* the conflict for a human, not be refused by the database. A test must provoke a real `23P01` (Prisma will not surface it as `P2002`) and a test must insert directly against the database and be refused. |
| D-3 | Time representation | **Two axes, branded, non-interchangeable: `CalendarDay`/`WallTime` (rules) vs `Instant` (occurrences). One conversion module; its `resolve()` returns `unique \| gap \| ambiguous`, never a bare instant. `CalendarDay` is stored `CHAR(10)`, never `@db.Date`.** | Rules (weekly windows, override days) are wall-clock; everything booked is an instant; the engine unions windows *after* resolution, never before (spec DST-7). Banned repo-wide by lint: `new Date(string)`, `Date.parse`, `get/setHours`, `toISOString().slice(0,10)`, `getTimezoneOffset`. Prisma `@db.Date` is banned because Postgres `date` → JS `Date` is the exact path that cost rental R-042 a day-west shift with ten green tests. CI runs the suite under `TZ=Pacific/Kiritimati` and `TZ=UTC` and asserts byte-identical output — a UTC-only CI lets axis-crossings ship. Temporal (via `temporal-polyfill`) at the boundary only; the engine core does integer epoch-millis arithmetic, which is DST-proof by construction and keeps the pure function library-free. |
| D-4 | Slot identity & grid | **A slot's identity is its instant. No URL, token, form, or job payload ever carries `{date, time}` — on fall-back day "01:30" names two instants and such a payload is a coin flip. Grid anchors to window-open, not local midnight.** | The booking POST takes an instant (offset-bearing ISO string). Fall-back's doubled hour is offered as two distinct slots with the offset visible (`labelIsAmbiguous`); spring-forward's missing hour produces no labels and a POST for a nonexistent local time is refused, never coerced. `'local-midnight'` anchoring shifts the whole grid twice a year; window-open is stable. Labels are precomputed server-side in the business zone — the browser's zone renders at most a secondary "your time" line. |
| D-5 | Manage-token lifetime | **Multi-use until `appointment.end + 24h`, scoped to one appointment, revocable by reissue, re-pointed (not reissued) on reschedule.** Rental D-16, same reasoning, same direction: the draft's "used tokens fail safely" is rejected. | Confirm-then-later-cancel and reschedule-twice are the *ordinary* customer workflow; a single-use token fails on step two of every appointment. Single-use remains correct where a token establishes a session (staff password reset). The control set instead: single-appointment scope, expiry, revocation on reissue, rate limiting on the route, and D-10's no-internal-identifiers rule with a test. |
| D-6 | Reschedule mechanics | **Reschedule is an event on a surviving appointment — a single-row `UPDATE` inside one transaction that re-runs the engine, plus an `AppointmentEvent` recording both sides. It is not a status, not a cancel-then-book, and not a new row.** | The PO review proposed old-row-`rescheduled` + new row; the concurrency spec showed why same-row wins and the tiebreak is the token: a new row kills the manage link at exactly the moment the customer is using it, and cancel-then-book across two transactions can leave the customer with *no* appointment (spec §4.6, four failure modes). History survives in the event log, which is append-only — nothing is lost by updating the row. The exclusion constraint checks the updated row against *other* rows only, so a move overlapping its own old time does not false-conflict. Cancellation-rate reporting reads events and excludes reschedules (RPT-03). Customer reschedule obeys the cancellation cutoff (APPT-05) — otherwise the cutoff is decorative. |
| D-7 | Lifecycle shape | **Eight states — `booked, confirmed, checked_in, in_progress, completed, no_show, cancelled, cancelled_late` — with the §7 transition table normative, `confirmed` given a real trigger, actual-vs-scheduled timestamps, and staff-only terminal corrections within 7 days.** | Adopts operator recs 1, 6, 7 wholesale: a book that cannot represent "actually started" or "running late" is a paper-book generator; `cancelled_late` split from `cancelled` because lumping them makes the cancellation report unactionable; `no_show ↔ completed` corrections exist because mis-taps are daily and the alternative is SQL surgery. Every status-reading predicate (constraint `WHERE`, reminder eligibility, busy-set query, day-view lists) is enumerated in one module — the rental "a status enum is never one edit" trap, headed off structurally. `no_show` and `completed` still occupy their time in the busy set; only the cancelled pair frees it. |
| D-8 | Staff overrides vs Goal 2 | **"Impossible" means impossible *by accident*. Customer self-serve can never create a conflict. Staff can knowingly double-book, book outside hours, or book into a buffer — reason required, audit event written, override marker rendered.** | The operator's hardest-won point: every platform he abandoned died of a flat refusal. Mechanically the constraint stays absolute and overrides are *modeled*: an override booking writes `blockedStart = blockedEnd` (zero-width range participates in no `&&` overlap) plus `overriddenFromRange` for display, so the constraint never lies and the day view renders the true collision. The alternative (dropping the constraint to app-level checks for staff) re-opens the accidental-double-book hole and is rejected. |
| D-9 | Staff auth in v1 | **One shared owner credential, real session, `actor ∈ {staff, customer_token, system}` stamped on every mutation. Multi-user staff auth and roles are Phase 3.** | Without an actor there is no "blocked for customers, allowed for staff" cutoff, no audit log worth the name, and the day view is publicly reachable. Minimal is fine and is stated as minimal so nobody builds Auth.js role machinery in month one. |
| D-10 | Tenant-facing lexicon | **One word per concept on customer surfaces; no internal identifier, entity name, or status enum renders on any token-reachable route — and a test asserts it.** Mirrors rental D-10/storage D-15. | **appointment** (not booking/slot on customer surfaces), **confirm**, **reschedule**, **cancel**. `no_show`, `cancelled_late`, backlog IDs and enum values stay on staff screens. One formatter for customer-facing times: business zone, abbreviation visible whenever the label is ambiguous. |
| D-11 | Lead time & cutoff coupling | **`minimumLeadMinutes` exists (draft omitted it), defaults 120, and startup validation enforces `minimumLeadMinutes ≥ cancellationCutoffMinutes`.** Cutoff is Business config, overridable per Service (`service.cutoff ?? business.cutoff`). | Closes the derivable product bug: with a 2h cutoff and no lead time, a customer books a slot 5 minutes out and is instantly unable to cancel it — trapped by design, phone call required, which is the failure the product exists to eliminate (spec §3.K). |
| D-12 | Segments, resources, multi-service visits | **The low-regret schema shapes land in Milestone 1; the features land in Phase 3 / late Phase 2.** `ServiceSegment` exists with exactly one ACTIVE segment per service in v1; `ResourceType`/`Resource` exist unreferenced by the engine; `AppointmentServiceLine` is plural-shaped with v1 flows creating one line. | The rental D-13 pattern: the schema affordance costs a column and a join; retrofitting segments onto a single-duration engine, a second constraint axis onto a live exclusion constraint, or plural lines onto a single-service appointment costs every query and a migration. The operator is right that segments/resources are where a colourist's Saturday revenue lives — and they are also a two-resource constraint problem that should not be tackled before the one-resource engine is green against its matrix. The engine's `SlotQuery` shape must not preclude a second busy-calendar input. |
| D-13 | Speculative fields | **No `payment_status` column. `businessId` on every core table stays.** | An always-null enum is a field every session must reason about and no test covers, and payments-when-they-come are rows, not a status (operator "do not build"; PO defect 29). `businessId` is the opposite case: free now, touches every query if retrofitted. |
| D-14 | Notification seam | **The outbox + `ChannelAdapter` with a logging adapter is Milestone 1 infrastructure, built before the first thing that sends.** Rental D-15's shape, adopted before the failure instead of after. | The confirmation email exists at BOOK-06 — before the reminder job — so without the seam, sending gets hand-rolled at call sites and the outbox arrives to find three of them. `NOTIFICATIONS_ENABLED` and sandbox redirect ship with the seam. Real Resend/Twilio drivers are a later one-assignment swap and are out of v1 scope entirely. |
