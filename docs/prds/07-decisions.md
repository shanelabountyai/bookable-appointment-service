| D-2 | What enforces "no double-booking" | **The database. A partial gist exclusion constraint on `(providerId, tstzrange(blockedStart, blockedEnd, '[)')) `, `WHERE status NOT IN (terminal set)`, in a hand-written migration.** Application code writes and maps SQLSTATE `23P01` → `SlotTaken` → 409; it never checks-then-writes as the correctness mechanism. | This is the schema-determining decision the draft left open, and it is item-one work: buffers live **inside** the stored blocked range (`blockedStart = startAt − bufferBefore`, `blockedEnd = endAt + bufferAfter`, stored columns); intervals are half-open everywhere or back-to-back bookings false-conflict; `READ COMMITTED` suffices *because* the constraint exists — no retry loop, no SERIALIZABLE (spec §4.3). | D-3 | Time representation | **Two axes, branded, non-interchangeable: `CalendarDay`/`WallTime` (rules) vs `Instant` (occurrences). Prisma `@db.Date` is banned because Postgres `date` → JS `Date` is the exact path that cost rental R-042 a day-west shift with ten green tests. CI runs the suite under `TZ=Pacific/Kiritimati` and `TZ=UTC` and asserts byte-identical output — a UTC-only CI lets axis-crossings ship. Temporal (via `temporal-polyfill`) at the boundary only; the engine core does integer epoch-millis arithmetic, which is DST-proof by construction and keeps the pure function library-free. |
| D-4 | Slot identity & grid | **A slot's identity is its instant. Labels are precomputed server-side in the business zone — the browser's zone renders at most a secondary "your time" line. |
| D-5 | Manage-token lifetime | **Multi-use until `appointment.end + 24h`, scoped to one appointment, revocable by reissue, re-pointed (not reissued) on reschedule.** Rental D-16, same reasoning, same direction: the draft's "used tokens fail safely" is rejected. | Confirm-then-later-cancel and reschedule-twice are the *ordinary* customer workflow; a single-use token fails on step two of every appointment. | D-6 | Reschedule mechanics | **Reschedule is an event on a surviving appointment — a single-row `UPDATE` inside one transaction that re-runs the engine, plus an `AppointmentEvent` recording both sides. It is not a status, not a cancel-then-book, and not a new row.** | The PO review proposed old-row-`rescheduled` + new row; the concurrency spec showed why same-row wins and the tiebreak is the token: a new row kills the manage link at exactly the moment the customer is using it, and cancel-then-book across two transactions can leave the customer with *no* appointment (spec §4.6, four failure modes). History survives in the event log, which is append-only — nothing is lost by updating the row. The exclusion constraint checks the updated row against *other* rows only, so a move overlapping its own old time does not false-conflict. Cancellation-rate reporting reads events and excludes reschedules (RPT-03). Customer reschedule obeys the cancellation cutoff (APPT-05) — otherwise the cutoff is decorative. |
| D-7 | Lifecycle shape | **Eight states — `booked, confirmed, checked_in, in_progress, completed, no_show, cancelled, cancelled_late` — with the §7 transition table normative, `confirmed` given a real trigger, actual-vs-scheduled timestamps, and staff-only terminal corrections within 7 days.** | Adopts operator recs 1, 6, 7 wholesale: a book that cannot represent "actually started" or "running late" is a paper-book generator; `cancelled_late` split from `cancelled` because lumping them makes the cancellation report unactionable; `no_show ↔ completed` corrections exist because mis-taps are daily and the alternative is SQL surgery. | D-24 | Serializing the booking write path | **The booking transaction takes a transaction-scoped advisory lock on `(providerId, businessDay)` before re-running the engine.** It is NOT the correctness mechanism for overlap — the D-2 exclusion constraint remains that, and is still tested against a writer that bypasses the lock. The lock closes the one gap the constraint deliberately does not cover. | A staff override stores a ZERO-WIDTH blocked range (D-8) so the constraint stays absolute without refusing the override — which means the constraint does **not** defend overridden time, and only the in-transaction engine re-check does (operator review R-9). Two concurrent transactions — a staff override and a self-serve booking of the same range — would both pass their re-checks and both commit, producing exactly the accidental double-book Goal 2 forbids. `pg_advisory_xact_lock` locks a KEY rather than a row, so it works before the row exists (`SELECT ... FOR UPDATE` cannot: the first booker of a slot finds nothing to lock), and the `_xact_` variant is released at COMMIT/ROLLBACK with no cleanup path to forget. Scope is one provider-day, so it costs nothing at salon scale. **Consequence worth knowing:** the spec's scripted "A reads, B reads, B commits, A writes → A gets 23P01" interleaving is no longer reachable through the write path — the loser now re-runs the engine after the winner commits and finds the time occupied. That is a stronger guarantee, and the write path maps an occupied slot to the same `SlotTaken` → 409 the constraint violation maps to, so the caller cannot tell the difference. The constraint's own defence is proven by a separate test that bypasses the lock. Prisma's interactive-transaction timeout is raised to 15s because queue time behind the lock counts against it and would otherwise surface as P2028, which looks nothing like a conflict. |
