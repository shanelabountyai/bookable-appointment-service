# Decisions — Bookable MCP server (M-track)

Decisions the MCP PRD (`docs/prds/mcp/00-mcp-prd.md`) does not answer, taken
by the builder with the recommended default and kept here so they can be
overruled. Bookable's own log is `docs/prds/07-decisions.md`; it still wins
over anything here that touches the product. Numbered `M-D`.

| # | Question | Decision | Why / restore |
|---|---|---|---|
| M-D1 | How is the channel (`desk`/`mcp`) recorded on `AppointmentEvent` (OQ-M1)? | **Optional `channel` on the core `Actor` type, and a `channel` column on `AppointmentEvent` defaulting to `desk`. MCP builds its actor with `channel: 'mcp'`; every existing writer is untouched.** Lands with M-009. | One migration, no reader changes. The alternative — a `channel` parameter on every domain function — is a signature change in a dozen places for one caller. |
| M-D2 | Where does the M-track log its decisions? | **This file, at the repo root**, cross-referenced from `07-decisions.md` when a decision touches the product (M-D1 will). | The brief asked for `DECISIONS.md`; the product's log keeps its D-numbers unbroken. |
| M-D3 | What is the gate per step? | **lint + typecheck + unit suite + `next build` before every commit. The full e2e sweep only on steps that change `apps/web` (M-002, M-014) and once at the end.** Push after each step and watch CI. | The MCP server is never rendered by the web app; a 9-minute browser sweep per step would test nothing it changed. CLAUDE.md's gate stays the rule for anything touching `apps/web`. |
| M-D4 | Hand-roll JSON-RPC or take the SDK? | **`@modelcontextprotocol/sdk` (pinned 1.32.1) + `zod` 4.** | Hand-rolling is more code and gets the capability negotiation subtly wrong. First new runtime dependency since the scaffold; it lives only in `apps/mcp`. |
| M-D5 | Does `list_services` show prices to `staff`, given D-36 (owner is the only role that sees money)? | **Yes.** The desk booking panel (`/staff/book`) already shows every stylist the price list; D-36's "money" is the dashboard and reports. | MCP mirrors the desk, not a stricter version of it. `get_week_report` stays owner-only. |
| M-D6 | How does M-001 run before tokens exist (M-002/M-003)? | **`BOOKABLE_MCP_STAFF_ID` env var, resolved with `findStaffById`, marked M-001 ONLY in `context.ts`.** Deleted by M-003 as planned; the only credential is `BOOKABLE_MCP_TOKEN`. | A staff id is not a credential; it is removed the moment a credential exists, not left as a fallback. |
| M-D7 | What does a revoked token get mid-session, given §6's table has no code for it? | **Two codes beyond §6: `UNAUTHORIZED` (token revoked, or its person off the roster — re-resolved on EVERY call, not per connection) and `FORBIDDEN` (role demoted since the listing was built). Neither carries `next`: the model cannot fix either, the human asks an owner.** | A Claude Desktop session stays connected for hours; checking the credential once at connect would make "deactivation revokes on the next call" false for the rest of the day. One indexed lookup per call, which also keeps `lastUsedAt` honest. |
| M-D8 | §6's code table has no code for a malformed argument, and a wall time cannot name one of two instants on fall-back day — how does the model pick? | **`INVALID_ARGUMENT` (with `field`) for anything zod or a `*Rejected(field, …)` refuses that no better code covers. And `start`-style inputs accept EITHER `YYYY-MM-DD HH:MM` in the salon's zone OR an ISO-8601 instant with its offset; an `AMBIGUOUS_TIME` refusal names both readings as ISO strings and tells the model to send one back.** | Slot identity is the instant (D-4, spec FB-2): after "01:30 happens twice" the only honest way to choose is to name the instant. `AMBIGUOUS_TIME` carries no `next` because the choice is the human's. Reasons are split ONCE in `errors.ts`: hours-ish reasons → `OUTSIDE_HOURS`, anything with a booking/buffer/chair overlap → `SLOT_TAKEN` (one taken reason wins, so an hours refusal can never hide a double-book). |
| M-D9 | `find_open_times` (§7) has no `client_id`, and does not say what "any" returns per time. | **It takes an optional `client_id`, threaded as `holderKey` exactly as `/staff/book` does (A-082/A-083). With `"any"`, each instant is listed ONCE under the stylist the desk would assign, carrying `free_count` (how many qualified stylists are free then); with a named stylist, every instant of her column.** | The offer must ask the question the write will ask: `prepare_booking` has the client, so an offer computed without her is stricter or looser than the room's answer, and the equality test (`availability.test.ts` › EQUALITY) is what keeps the two paths honest — `anyProviderTimes` is the desk's "no preference" path and already answers per instant, not per stylist. |
| M-D10 | What exactly does `get_appointment` return as `allowed_actions`, and which free text travels (OQ-M3 says client notes do not)? | **`allowed_actions` is a list of `{action, tool, to?}` built from `availableTransitions` (only the four statuses `prepare_status_change` accepts, named `check_in`/`start`/`complete`/`no_show`), `canCancel` + `staffCancellationStatus` (`to` says `cancelled` or `cancelled_late` before anyone commits), and `canReschedule` — with the staff detail page's context, `reason: 'placeholder'` included. The BOOKING note travels (it is what the desk typed for this visit and `prepare_booking` can write one); CLIENT notes and phone numbers never do, on any of `get_day`, `get_appointment`, `find_client`, `get_client_history`.** | A second `if (status === …)` is the rental VERIFIED defect; the EQUALITY test in `day.test.ts` walks booked → checked_in → in_progress → completed and requires the tool and the table to agree at every step. Naming the tool per action removes a guess the model would otherwise make. |
| M-D11 | What does `get_week_report` carry, given the dashboard shows two utilization numbers and no money? | **Exactly the dashboard's `dashboardSummary`: bookings, cancels (normal/late/overruled), no-shows by stylist, and per stylist BOTH fractions — `used` (RPT-02, visits that happened) and `spoken_for` (D-51, booked whether or not happened). No money: the dashboard shows none, so the PRD's "any money figures that report already shows" resolves to nothing.** Owner-only by `roles`, so a stylist's call is refused by the protocol ("tool not found") before any handler runs. | Mirroring the screen keeps one source of truth; a stylist's token cannot even learn the tool's name. |
| M-D12 | What happens to a proposal whose commit is REFUSED by the domain function (slot taken, status moved), and how does a retried commit behave? | **The claim stands: `usedAt` is set before the write, the refusal is recorded in `outcome`, and the model is told to re-prepare (`next` = the `prepare_*` tool). A proposal is never retried, because the world it previewed is gone. The booking commit passes `idempotencyKey: mcp:<proposalId>` to `bookAppointment`, so a commit whose response was lost returns the SAME appointment (`deduplicated: true`) rather than a second one. `argsHash` is over key-sorted JSON (`canonicalJson`): `jsonb` reorders keys, and a hash of insertion order refused every proposal it stored — found by the first commit test.** | §8's "nothing is half-written" plus §6's "every error names what to do next". Un-claiming on failure would invite a retry loop against a stale preview. |
| M-D13 | `prepare_new_client(name, phone)` when the phone is already on the books? | **Refused with `AMBIGUOUS_CLIENT` naming the existing client(s) and their ids, `next: find_client`.** The desk's own "add somebody" would create a duplicate; the model is held to a higher bar because it cannot see the list the desk can. | A model that has just been told "no client matches Maria" and then gets a phone will try to add her; the phone lookup is the one fact that catches a second record for one person. |
| M-D14 | How do the status-changing commits guard against the row moving between preview and commit, and how is the MCP-level race proven? | **Every `prepare_cancel` / `prepare_status_change` proposal stores `expected_from` (the status it previewed) and the commit passes it as `transitionAppointment`'s `expectedFrom`, so a desk tap in between yields `AppointmentMovedFirst` → `PROPOSAL_STALE`, never an overwrite; `prepare_reschedule` relies on the table (`RescheduleRefused` → `INVALID_TRANSITION`) and the engine (`SlotTaken`). The race is proven two ways: one proposal committed twice behind `behindRowLock('McpProposal', …)` — the row is held until both commits are queued on it, so both read it unused and exactly one claim succeeds; and two proposals for one slot committed together, serialised by `bookAppointment`'s advisory lock (the domain layer's own deterministic test, races.test.ts #1).** | Spec §4.5: specify the interleaving, don't sample it. The claim is the only MCP-owned race; the slot race belongs to the domain layer and is tested there with barriers already. |
| M-D15 | OQ-M5: can the target clients send a static bearer token over HTTP, and how is the HTTP transport shaped? | **Verified 2026-10-12 against the current docs. Claude Code: yes — `claude mcp add --transport http bookable <url>/api/mcp --header "Authorization: Bearer bk_mcp_…"`. claude.ai / Claude Desktop custom connectors: a static header only as an ORGANISATION-level credential an Owner enters once (Team/Enterprise); otherwise OAuth. So M-014 ships bearer-over-Streamable-HTTP for Claude Code, Desktop keeps stdio (local), and OAuth stays a later item. The route is STATELESS (no session id; one server + transport per request) with JSON responses rather than SSE — a Vercel function keeps nothing between requests, and every tool here answers in one message. `/api/mcp` is exempt from the demo Basic gate because the bearer travels in the same `Authorization` header.** | Sources: code.claude.com/docs/en/mcp ("Option 1: Add a remote HTTP server"), claude.com/docs/connectors/building ("Choose how users authenticate"). Stateless costs one token lookup per request, which the per-call refresh (M-D7) already paid. |
| M-D16 | Where does the §6 error envelope travel, and how is a same-time stylist change committed? | **(1) In `content` as JSON text ONLY — never in `structuredContent`. (2) `prepare_reschedule`'s commit routes an unchanged instant with a new stylist to `reassignAppointment` (the desk's sick-stylist path) and everything else to `rescheduleAppointment`; the preview is the same for both.** Both found by the eval harness's scripted dry run, not by any unit test. | (1) A client that has called `tools/list` validates `structuredContent` against the tool's output schema whether or not `isError` is set, and refuses the whole result — every error would have reached Claude as an SDK exception rather than a recoverable envelope, and nine suites of unit tests never saw it because none called `tools/list` before `tools/call`. (2) `rescheduleAppointment` refuses an unchanged instant as `already-at-that-time`; the sick-stylist scenario is the one place the two domain functions are one operational question. |
| M-D17 | How does the model eval (§9.7) run, and with what? | **`apps/mcp/eval`: nine scenarios graded on the DATABASE end state; a `Model` interface with `ClaudeModel` (Anthropic SDK, `EVAL_MODEL` default `claude-opus-5-5`, stable `messages.create`, no forced `tool_choice`, no server-side fallback beta) and `ScriptedModel` (replays each scenario's ideal tool path, zero cost). The scripted run is in CI (`harness.test.ts`); the Claude run is MANUAL (`npm run eval`), per-scenario cost cap `EVAL_COST_CAP_USD` (default $1.00) from a pricing table, turn cap 24, results in `eval/results/` (gitignored). Not run in this build: it spends API credit, which is the owner's call (STATUS.md names the command).** | §9.7 says "manual, not CI" and "cost cap per run, recorded". The scripted path proves the harness and every grader without spend, and the three negative tests prove a pass means something. |
| M-D18 | What closes the M-track in this build, and what is left for the owner? | **Closed here: code, tests, gate, `apps/mcp/README.md`, `docs/DEMO.md` §13, `STATUS.md`, the "via the assistant" audit line on the detail page. Left for the owner, each named in `STATUS.md`: connecting a real client, the Claude eval run (spends credit), the deploy (the brief said not to), the exec brief and LinkedIn drafts (they publish).** | The brief: no deploy, no external writes, log and default. The definition of done's artifacts 2–3 publish to claude.ai, so they are hand steps with the source material (`RELEASE_NOTES.md` M-001..M-016) ready. |
